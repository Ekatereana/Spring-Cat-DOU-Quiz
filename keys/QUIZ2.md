## Справа №1. Міграція, яка нічого не зберігала  (`./gradlew q07`)

**Тікет:** перед справжньою міграцією прогнали «сухий» прогін на проді: прочитати рядки,
нормалізувати імена в памʼяті, порахувати, скільки зачепить. Жодного `save()`, жодного `flush()`.
Звіт подивились, реліз відкотили. Наступного дня — помилки валідації на іменах, яких ніхто
не змінював.

```java
@Transactional
public int preview() {
    int wouldChange = 0;
    for (Cat cat : repo.findAll()) {
        String normalised = cat.name.trim().toLowerCase();
        if (!normalised.equals(cat.name)) {
            cat.name = normalised;            // «це лише щоб вивести діф»
            wouldChange++;
        }
    }
    return wouldChange;                       // save() немає
}
```

- A) Нічого не буде: без `save()` Hibernate про зміни не знає
- B) На коміті Hibernate зробить auto-flush, порівняє сутності зі снапшотами й виконає `UPDATE`
  на кожен змінений рядок
- C) `UPDATE` буде, але тільки після явного `entityManager.flush()`
- D) Полетить виняток: міняти сутність без `save()` не можна

**Правильно: B.** Усе, що повернув репозиторій **усередині транзакції**, — керовані (managed)
сутності. Hibernate робить снапшот при завантаженні, а на коміті — auto-flush і **dirty
checking**: що відрізняється, те й оновлює. `save()` потрібен лише для **нових** обʼєктів.

```
 @Transactional ─▶ findAll() ─▶ MANAGED + снапшот
                                     │
                   cat.name = "dobby" │  (save() ніхто не кликав)
                                     ▼
             коміт ─▶ auto-flush ─▶ dirty checking ─▶ UPDATE cat SET name=? WHERE id=?
```

«Я ж не комітив» теж не рятує: у `FlushMode.AUTO` Hibernate флашить ще й **перед запитом**,
який може зачепити змінені таблиці — `UPDATE` може полетіти в середині методу.

А відкат релізу не допоміг, бо транзакція **успішно завершилась**: відкочувати нічого,
реліз повертає код, не рядки.

| Що робимо | Рятує? | Чому |
|---|---|---|
| `@Transactional(readOnly = true)` | ✅ | сесія йде у `FlushMode.MANUAL` — автофлашу немає, снапшоти не беруться |
| проєкція або DTO: `select c.name from Cat c` | ✅ | керованих сутностей немає — dirty-check'ати нічого |
| `entityManager.detach(cat)` перед зміною | ✅ | сутність виходить з persistence context |
| «не кликати `save()`» / відкат релізу | ❌ | саме цим і впіймались |

Нюанс: `readOnly = true` не блокує явний `flush()`. Spring ще виставляє
`Connection.setReadOnly(true)` — Postgres на цьому заборонить запис на рівні бази, H2 і MySQL
прапор тихо проігнорують.

## Справа №2. Профайл, якого не було  (`./gradlew q08`)

**Тікет:** локально й на staging усе літає. На CI з `spring.profiles.active=test` застосунок
не стартує взагалі. Мок додали «щоб тести не ходили в реальний фідер».

```java
@Bean Feeder realFeeder() { return new RealFeeder(); }   // дефолт, без профайла

@Profile("test")
@Bean Feeder mockFeeder() { return new MockFeeder(); }   // мок для тестів

@Bean CatService catService(Feeder feeder) { ... }
```

Що станеться на CI?

- A) Spring візьме бін із профайла — профайл специфічніший за дефолт
- B) `NoUniqueBeanDefinitionException` на старті: бін без `@Profile` активний **завжди**, тож
  кандидатів два
- C) `mockFeeder` переб'є `realFeeder` — bean overriding
- D) Нічого не буде: `@Profile("test")` поза тестами просто ігнорується

**Правильно: B.** Відсутність `@Profile` — це не «дефолт», це «активний у всіх профайлах».
З `test` обидва визначення живі, а точка інʼєкції бачить два кандидати однакового типу.
C була б правдою лише за однакових **імен** бінів — тоді був би `BeanDefinitionOverrideException`,
бо з Boot 2.1 overriding вимкнений.

**Що робить?:** `@Profile("!test")` на дефолті · або `@ConditionalOnMissingBean` на моку ·
`@Primary`/`@Qualifier`, якщо обидва потрібні · вирази теж працюють: `@Profile("prod & !legacy")`.

## Справа №3. Фіча, яку забули ввімкнути  (`./gradlew q08`)

**Кейс:** нічну джобу біллінгу закрили профайлом `prod`, скедулер збирає джоби колекцією.
На dev профайл ніхто не вмикає.

```java
@Profile("prod")
@Bean NightJob billingJob() { ... }

@Bean Scheduler scheduler(List<NightJob> jobs) { ... }   // колекційна інʼєкція
```

Запускаємо без `prod`. Що буде?

- A) `NoSuchBeanDefinitionException` на старті
- B) Старт ок, у списку **0 джоб** — біллінг просто не існує, і ніхто про це не скаже
- C) Spring підсуне порожній проксі замість біна
- D) Впаде на першому запуску скедулера

**Правильно: B.** Колекційна точка інʼєкції приймає нуль кандидатів як легальний порожній список.
Одиночний `NightJob` впав би з `NoSuchBeanDefinitionException` — а `List<NightJob>` стартує
зелененьким. Фіча тихо вимкнена, хелсчеки зелені, рахунки не виставляються.

**Що робить?:** `Assert.notEmpty(jobs, ...)` або перевірка в `@PostConstruct` · логувати на старті,
скільки джоб підхопилось · для фічі, яку має бути видно, краще `@ConditionalOnProperty` + явний
health indicator, ніж профайл.
